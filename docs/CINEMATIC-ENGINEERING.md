# Cinematic engineering audit and scene guide

## Baseline and findings

The site is Astro 7.3.5, statically built with MDX and sitemap integrations, Sharp image processing, and GitHub Pages deployment (`astro.config.ts`, `.github/workflows/deploy.yml`). Pages and layouts generate HTML; no framework islands or animation libraries are installed. `BaseLayout.astro` loads one progressive-enhancement script. Navigation is normal document navigation, so browser document teardown currently owns global listeners. There is no client router.

- **Critical:** None verified by this audit. This is not a production monitoring or full accessibility audit.
- **High — fixed:** `site.ts` previously hid reveal targets before testing for IntersectionObserver support. On unsupported browsers the constructor could fail and content remain hidden. The product-lighting observer also lacked a feature check.
- **High — improved:** the demo and article videos requested metadata on initial load and automatic playback ignored tab visibility and changes to motion preference. The demo is a 6,729,300-byte, 1280×832 H.264 file, 29.47 seconds long. Metadata preload is only a browser hint, not a download guarantee. Native controls remain the fallback.
- **Medium — remaining:** the full-viewport ambient gradients and continuous CSS animations (`src/styles/global.css`) can impose paint/compositing costs; product sections use `content-visibility` with estimated intrinsic sizes (`src/styles/pages.css`), which can shift layout when estimates differ. Profile on actual mobile hardware before expanding either system.
- **Medium — remaining:** reveal, pointer, and lighting behavior is global and initialized once per document (`src/scripts/site.ts`). It has no reusable teardown contract for future client-side navigation. Do not add a client router without revisiting ownership. The current video module has explicit cleanup and is the reference for scoped enhancement.
- **Medium — remaining:** color, surface, typography, edge and container tokens are centralized in `src/styles/global.css`; section-specific sizes and breakpoints remain local. Buttons and reveals repeated duration values; the new motion tokens preserve their existing values. Accent and SIGMA cyan are intentional differences. Some low-contrast secondary text and decorative overlays need a dedicated contrast review against actual composited backgrounds.
- **Low:** no tests, lint, or formatter scripts existed. The small Node lifecycle test added here covers the new behavior; CI currently runs Astro check and build only. Font stacks are system fallbacks, so there is no webfont download or font swap. Images have intrinsic dimensions; the hero uses responsive AVIF/WebP with JPEG fallback and high priority. The logo is also prioritized on the home page. LCP, CLS, INP, network transfers, decoding pressure, and GPU costs have not been measured in a profiling session.

## Implemented reference: in-view video

`src/pages/products/sigma.astro` provides a poster, intrinsic dimensions, muted inline video, native controls, `preload="none"`, and `data-autoplay-in-view`. `src/scripts/site.ts` dynamically imports `src/scripts/video-playback.ts` only when an opted-in video exists. The module observes visibility, handles autoplay rejection, pauses automatic playback when hidden, honors motion preference changes and manual pauses, and returns a cleanup function. It disconnects its observer and listeners on ordinary page teardown; the back-forward cache retains the document. `src/components/article/Video.astro` uses the same opt-in for ambient media. The static poster and controls remain useful without JavaScript or when autoplay fails. This is a concrete lifecycle example, not a general scene engine.

## Adding a scene

1. Put meaningful content and a static image or poster in a named Astro component. Keep its assets near the subject (`src/assets/<subject>/` for processed images; `public/assets/<subject>/` for stable public URLs). Set intrinsic dimensions and accessible text. Give controls keyboard access; never depend on motion to explain the content.
2. Add a scene-specific TypeScript module only when enhancement is needed. Import it dynamically after proximity or a user gesture, and handle import failure without hiding the fallback. Avoid a registry until multiple real scenes need one.
3. Let the scene own its timeline or its single animation-frame loop, event listeners, observers, resize handling, timers, network requests and rendering resources. Expose cleanup; disconnect/cancel/abort and dispose renderer resources on removal. Pause on invisibility and `document.hidden`; resume only work that was active. Account for asynchronous loads completing after teardown. For client navigation, explicitly remount and unmount; ordinary full-page navigation alone is not a reusable lifecycle.
4. Read `prefers-reduced-motion` initially and on change. Supply a stable, informative static state and keep controls usable. Avoid scroll-driven layout reads on every event; derive progress from a single owner and test resize and reverse scrolling. Separate renderer state from UI state.
5. Layer HTML, SVG, Canvas or WebGL within a deliberately positioned scene; document stacking and pointer events. For canvas use ResizeObserver, cap device pixel ratio based on measurements, and disconnect it on teardown. For WebGL handle context loss/restoration and dispose textures, geometry and renderer. Do not allocate a WebGL context for static content.
6. Verify no-JS, keyboard, reduced motion, narrow and wide viewports, loading and error states, repeated mount/unmount, visibility transitions, and lower-powered devices. Record network, frame and memory profiles before choosing budgets or libraries.

Use CSS transitions and the Web Animations API for suitable DOM motion today. Anime.js or GSAP may be dynamically imported by a scene when its actual sequencing needs justify the cost; evaluate current versions, licensing, accessibility and bundle impact at that time. Three.js, PixiJS or custom WebGL should likewise be scene-local, deferred and justified by a real 3D or high-volume 2D workload; Canvas 2D or SVG may suffice. No candidate library was installed or compatibility-tested because no current scene needs one. There is no common lifecycle abstraction or manifest yet: one concrete video module is insufficient evidence for either.

## Media delivery

- Critical viewport images: use Astro `<Picture>` with responsive widths, `sizes`, appropriate formats and explicit priority only for the actual LCP candidate. Near-viewport images: native lazy loading. User-triggered/expensive scenes: render a poster first and load the renderer and media on proximity or interaction. Do not preload a whole sequence.
- Keep genuine captures and rights/credits with each asset. Record dimensions, duration, encoding, poster and attribution alongside a scene when multiple assets justify metadata; avoid an empty speculative manifest. H.264 MP4 is the current broad fallback. Evaluate WebM/AV1, transparent overlays and codec support per actual source and target devices; retain a static fallback. Supply captions/transcripts for meaningful audio and controls for meaningful video.
- `src/assets` images are built into hashed files; `public` URLs are copied unchanged and require deliberate versioned filenames or cache invalidation when content changes. GitHub Pages controls delivery headers; validate range requests, caching and CDN behavior before moving large media to external hosting, including CORS, privacy, cost and licensing implications.
- Multiple videos compete for bandwidth and hardware decoders. Limit concurrent active previews and loading, choose representative stills, and measure on mobile. Coordinate synchronized media from one scene clock, handle buffering/drift and avoid assuming frame-accurate HTML video seeking. Use abortable fetches where fetching is truly required; native media loading has its own lifecycle. Expose retry when a scene has actionable failure states.

## Proposed budgets, not measured guarantees

Current production output after the change is approximately 3.9 KB shared JS, 1.4 KB conditional video JS, and 28 KB shared CSS, all uncompressed; the video itself is 6.42 MiB. These are file sizes, not transferred bytes or runtime benchmarks. Starting review targets: keep shared JS below 10 KB compressed, each optional scene below 50 KB compressed before its renderer, initial image transfer below 500 KB on a representative mobile viewport, and initial video transfer at zero until the browser chooses otherwise or playback starts. Treat those as goals, not enforcement or proof. For active animation aim for 60 fps where practical and avoid long tasks over 50 ms; measure LCP, CLS and INP on representative devices and networks before setting firm limits. Video byte budgets must be established per real sequence, quality and duration.

## Prioritized follow-up

1. Profile the existing ambient layers and product page on mobile; audit contrast, real loading and layout shift. Add browser-based lifecycle and reduced-motion coverage to CI when a supported browser test setup is chosen.
2. Animated SIGMA hero: begin with the existing responsive screenshot, then add one scoped, optional transform/timeline enhancement with a static reduced-motion state.
3. Exploded workflow: start with accessible HTML/SVG and native or scene-local timeline control, with explanatory text available independently.
4. Multi-video showcase: prototype one poster-first scene, concurrency limit, loading/error states and synchronization on representative devices before scaling.
5. Interactive product demo: define a bounded, keyboard-operable workflow and realistic captures; isolate substantial state and defer any framework until needed.
6. GPU visuals: add Canvas/WebGL only after the visual and measured workload require it; implement context recovery and disposal within that scene.
